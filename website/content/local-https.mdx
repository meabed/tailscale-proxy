# Local HTTPS names

Every dev server on this machine gets a stable HTTPS name, for as long as it runs. Start it the way you always do:
tsp finds it and names it after its folder, or after the name in your project's config.

## Why a name instead of `localhost:3000`

- **HTTPS like production.** Secure cookies, `SameSite=None`, service workers, passkeys, the clipboard API and OAuth
  libraries that refuse plain HTTP all work.
- **Names, not ports.** You open `web.acme.localhost`, whatever port the server picked today; with `tsp run`, tsp picks
  a free port for it, so two projects that both want port 3000 stop colliding.
- **Names that say what they are.** `api.acme.localhost` and `web.acme.localhost` instead of two numbers; cookies
  scoped to `.acme.localhost` are shared between them.
- **Subdomains per tenant.** With `help-chat` running, `https://acme.help-chat.localhost` reaches it too.

## Set up a machine (once)

```bash
tsp service install    # the proxy from boot + the CA trusted; re-run any time, it fixes what is off
tsp service status     # three ✓ lines, exit 1 when one is off
```

## Start your app as usual

```bash
cd ~/acme/web && npm run dev          # Vite on 5173, as always
```

```
$ tsp routes
NAME                                         FROM   PORT   FOLDER
https://web.localhost                        found  5173   ~/acme/web (node)
Live, with requests per name: https://tsp.localhost
```

No script changes, and nobody else on the project needs tsp. The local proxy looks for dev servers in your port range
(the one in [Configuration](/configuration), plus 4000–4999) and gives each the name of its project folder. It looks
every 10 seconds while you use the names and every minute otherwise, and it looks again the moment you open a name it
doesn't know yet, so a server you just started answers on the first request. A server that stops loses its name after a
few scans.

### Pick the name

Put the name in the project's config, in whichever file the project already has. The first one found in the project
folder wins.

    ```json

    ```

    Any language. Use it for Go, Ruby, PHP without Composer, or to keep the setting out of a shared manifest.

  </Tabs.Tab>

    name = "svc.acme"
    port = 8080
    ```
  </Tabs.Tab>

  </Tabs.Tab>

    ```

| Field | Default | What it does |
| --- | --- | --- |
| `name` | the folder's name | the app's address, `https://<name>.localhost` |
| `port` | the lowest port | which listener is the app, when the project runs several servers |
| `share` | your global mode | online with `tsp`: `"public"`, `"private"` (your tailnet only) or `false` (never) |
| `path` | the name's first label | the app's path online, `https://<machine>.ts.net/<path>/` |
| `enabled` | `true` | `false` keeps tsp away from the project entirely |
| `script` | none | for `tsp run` only (below) |

tsp reads a config file only if you own it and nobody else can write it, and never looks above your home folder or
inside a folder everyone can write, such as `/tmp`. A file it refuses or can't parse leaves the project out (nothing
falls back to defaults), and `tsp doctor`, `tsp routes` and the dashboard say which file and the command that fixes
it. To turn discovery off: `tsp configure --discover=false`.

The app receives the request with its own name as the host (`Host: web.acme.localhost`) and `X-Forwarded-Proto:
https`, `X-Forwarded-Host` and `X-Forwarded-For`. Vite and Next.js accept `*.localhost` as they come; Django and Rails
check the host:

```python
# Django settings.py
ALLOWED_HOSTS = [".localhost"]
CSRF_TRUSTED_ORIGINS = ["https://*.localhost"]
```

```ruby
# Rails config/environments/development.rb
config.hosts << ".localhost"
```

## Or run it through tsp

`tsp run` starts the server for you on a free port it keeps for that name (4000–4999), sets `PORT` and `HOST`, and
holds the name while the command runs: useful when two projects want the same port, or in scripts.

**In a `package.json` project**, keep the real command as its own script and point `dev` at tsp. `npm run dev`,
`pnpm dev`, `yarn dev` and `bun dev` all work: the script runs with the package manager that started it.

```jsonc
"scripts": { "dev": "tsp run", "dev:app": "vite --port $PORT --host $HOST --strictPort" },
"tsp": { "name": "web.acme", "script": "dev:app" }
```

**Anything else**: give the name and the command. A command in one quoted string runs through the shell after tsp
sets `PORT` and `HOST`; several arguments run as they are, for servers that read `PORT` themselves.

| `tsp run` sets | Value |
| --- | --- |
| `PORT` | a port in 4000–4999, the same for a name run after run while it is free |
| `HOST` | `127.0.0.1` |
| `NODE_EXTRA_CA_CERTS` | the local CA, unless already set, so Node and Bun trust other `.localhost` names |

A `tsp run` name wins over a found one. `tsp run --force` takes a name over from another terminal; `TSP=0 npm run dev`
runs the `dev:app` script as it is, without tsp. The name `tsp` is reserved for the dashboard.

## The dashboard

`https://tsp.localhost` shows what runs (how each was started, port, folder, uptime), requests, failures and p50/p95
per name, the proxy's version, live updates and set-aside releases, discovery and update status, and any config file
it skipped, with how to fix it. It updates itself every few seconds and is reachable only from this machine. The same
data as JSON for scripts and agents: `https://tsp.localhost/api/status`.

## Stop an app

A dev server left running in a forgotten terminal holds its port. Stop it by name or by port:

```bash
tsp stop web.acme        # the app at https://web.acme.localhost
tsp stop 3000            # whatever listens on port 3000
tsp stop web.acme --force
```

`tsp stop` shows what it is about to end (process, pid, port, folder) and the command it runs, then asks. It sends
SIGTERM, as Ctrl-C in the app's terminal would, and waits up to 5 seconds for it to exit; a `tsp run` app ends with
its `tsp run`. An app that ignores it is still running afterwards, and `--force` ends it at once (SIGKILL). On Windows
it runs `taskkill /PID <pid> /T`, and `/F` with `--force`. `--yes` skips the question, for scripts and agents.

On the dashboard, each app has a **Stop** button. It opens the same summary, the exact command the button runs, and
the commands that do the same in a terminal on this OS, each with a copy button:

| | macOS, Linux | Windows |
| --- | --- | --- |
| Stop | `kill <pid>` | `taskkill /PID <pid> /T` |
| Force | `kill -9 <pid>` | `taskkill /PID <pid> /T /F` |
| By port | `lsof -ti tcp:<port> -sTCP:LISTEN \| xargs kill` | `Get-NetTCPConnection -LocalPort <port> -State Listen \| ForEach-Object { Stop-Process -Id $_.OwningProcess }` |

The same through the API: `GET https://tsp.localhost/api/apps/<name>` returns what a stop would end and how, and
`POST https://tsp.localhost/api/apps/<name>/stop` with `{"force": false}` stops it (200 when it exited, 409 with the
forced command when it did not). Only the dashboard's own page can stop an app from a browser: tsp refuses a request
another website sends (it checks `Sec-Fetch-Site` and `Origin`, and asks for a JSON body, which a form cannot send).
On macOS and Linux the request must also come from one of your own programs, never another account's on the same
machine.
tsp never stops itself, a process another user owns, or Docker: for a container's port it names the container to
`docker stop` instead.

Opening a name that nothing runs under shows the names that do run and how to start an app under that one; a name
whose app stopped answering shows its port, process, folder and the likely cause. A browser gets a page, curl gets the
same as text.

## Plain HTTP

`http://` gets what `https://` gets. Every `http://<name>.localhost`, the reserved `tsp` included, redirects to the same
URL over https (308: the method and body are kept), so a browser shows the very same page. `http://localhost/` and
`http://127.0.0.1/` open the dashboard, like `https://localhost/`. Any other host that reaches port 80 gets a short 404
that lists nothing, so a website whose name was re-pointed at 127.0.0.1 (DNS rebinding) learns nothing about this
machine. If another program holds port 80, HTTPS keeps
working and `tsp doctor` names the program.

## Subdomains

A name also answers for its subdomains: with `help-chat` running,
`https://acme.help-chat.localhost` reaches it too (the nearest registered parent wins),
for apps that serve one tenant per subdomain.

## Technical details

- **Found servers** live in the proxy's memory: each scan lists the listening sockets in the port range with their
  process (reusing what it learned about each process, so an idle scan costs one `lsof`), keeps the web runtimes, finds
  each one's project folder and config, and maps names to ports. A project that runs several servers gets its main name
  on the lowest port (or the config's `port`) and `<name>-<port>` for the others.
- **`tsp run` names** are one JSON file per running app in `~/.tsp/routes/<name>.json` (`{name, port, pid, dir}`) and a
  lock its process holds. Both go when the run ends, and the proxy drops the name of a run killed with `kill -9` the next
  time it reads the folder, which it does only when the folder changes.
- **Certificates**: a local CA in `~/.tsp/ca/` (ECDSA P-256, 10 years, key
  `0600`) signs one certificate per exact name on first use (90 days, renewed in memory).
  The CA carries a name constraint for `localhost`: it cannot sign a certificate for any
  other domain that a browser would accept. Names outside `.localhost` get no certificate,
  and the cache is bounded.
- **The service** is a small supervisor that runs as root for one job: opening
  `127.0.0.1:443` and `[::1]:443`, which an ordinary process cannot do. It then switches to
  your user for good, keeps the sockets open for its whole life, and runs the proxy as a
  worker from your own copy of tsp in `~/.tsp/bin`. Root never runs a file you can write,
  and every file the proxy writes stays yours. While no worker runs, the supervisor serves
  the names itself, so they keep working. macOS: a launchd daemon
  (`/Library/LaunchDaemons/com.meabed.tailscale-proxy.plist`, log
  `/var/log/tailscale-proxy.log`). Linux: a systemd unit (`tailscale-proxy.service`,
  `journalctl -u tailscale-proxy`).
- **Updates without a password or a dropped request**: any newer tsp you run copies itself
  into `~/.tsp/bin` (never an older one), and the proxy checks for a release once a day and
  verifies it against the release's `checksums.txt`. The supervisor starts the new version
  beside the serving one on the same sockets; once it answers a real HTTPS request it takes
  over and the old worker drains. A version that fails, or crashes within its first minute,
  is recorded as set aside in `bin/state.json` and never used again; the previous worker
  keeps serving. A crashing worker restarts with backoff. sudo is needed again only if the
  supervisor itself changes, which `tsp doctor` says. `tsp run` in a terminal sets up a machine that has no proxy yet; in CI or
  a pipe it only warns.
- **Trust**: `tsp service install` ends with it (or `tsp trust` alone). macOS adds the CA
  to your login keychain (one password dialog at the screen; over SSH it is left as a
  next step). Debian/Ubuntu: `/usr/local/share/ca-certificates` +
  `update-ca-certificates`; Fedora/RHEL: `/etc/pki/ca-trust/source/anchors` +
  `update-ca-trust`. Windows: the user's Root store (`certutil -user`).
