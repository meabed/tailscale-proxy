# Local HTTPS names

`tsp run` starts an app on a free port and serves it at a stable HTTPS name on this machine, for as long as it runs.

## Why a name instead of `localhost:3000`

- **HTTPS like production.** Secure cookies, `SameSite=None`, service workers, passkeys, the clipboard API and OAuth
  libraries that refuse plain HTTP all work.
- **No port bookkeeping.** tsp picks a free port in 4000–4999 (the same one for a name, run after run, while it is
  free). Two projects that both want port 3000 stop colliding.
- **Names that say what they are.** `api.acme.localhost` and `web.acme.localhost` instead of two numbers; cookies
  scoped to `.acme.localhost` are shared between them.
- **Subdomains per tenant.** With `help-chat` running, `https://acme.help-chat.localhost` reaches it too.

## Set up a machine (once)

```bash
tsp service install    # the proxy from boot + the CA trusted; re-run any time, it fixes what is off
tsp service status     # three ✓ lines, exit 1 when one is off
```

## Run an app

```jsonc
// package.json
"scripts": { "dev": "tsp run", "dev:app": "bun --hot src/index.ts" },
"tsp": { "name": "api.acme", "script": "dev:app" }
```

```bash
bun dev                                   # → https://api.acme.localhost
tsp run api.acme -- bun src/index.ts      # any command, no package.json needed
tsp run --force                           # take the name over from another terminal
TSP=0 bun dev                             # run dev:app as is, on its own port
tsp routes                                # running names (--json for scripts)
```

The app gets:

| Variable              | Value                                                                    |
| --------------------- | ------------------------------------------------------------------------ |
| `PORT`                | a port in 4000–4999, the same for a name run after run while it is free  |
| `HOST`                | `127.0.0.1`                                                              |
| `NODE_EXTRA_CA_CERTS` | the local CA, unless already set (Bun/Node calls to other `.localhost` names) |

The app's script must listen on `$PORT` and `$HOST` (`vite --port $PORT --host $HOST`,
`next dev -p $PORT -H $HOST`; Bun and Hono servers read `PORT`). The script runs with the
package manager that ran `tsp run` (`npm_execpath`), so `bun dev` runs `bun run dev:app`.

A name also answers for its subdomains: with `help-chat` running,
`https://acme.help-chat.localhost` reaches it too (the nearest registered parent wins),
for apps that serve one tenant per subdomain.

Requests reach the app with the original `Host` (`api.acme.localhost`) and
`X-Forwarded-Proto: https`, `X-Forwarded-Host`, `X-Forwarded-For`. HTTP/2, streaming
(SSE) and WebSockets (Vite/Next hot reload) pass through.

## Technical details

- **Routes** are one JSON file per running app in `~/.tsp/routes/<name>.json`
  (`{name, port, pid, dir}`), written atomically by its `tsp run` and removed when it
  exits. A route whose `tsp run` process is gone is ignored and deleted on the next read,
  so a crash or `kill -9` never leaves a name behind. The proxy re-reads the folder only
  when it changes.
- **Certificates**: a local CA in `~/.tsp/ca/` (ECDSA P-256, 10 years, key
  `0600`) signs one certificate per exact name on first use (90 days, renewed in memory).
  The CA carries a name constraint for `localhost`: it cannot sign a certificate for any
  other domain that a browser would accept. Names outside `.localhost` get no certificate,
  and the cache is bounded.
- **The service** is a small supervisor that runs as root for one job: opening
  `127.0.0.1:443` and `[::1]:443`, which an ordinary process cannot do. It then switches to
  your user for good, keeps the sockets open for its whole life, and runs the proxy as a
  worker from your own copy of tsp in `~/.tsp/bin`. Root never runs a file you can write,
  and every file the proxy writes stays yours. While no worker runs, the supervisor serves
  the names itself, so they keep working. macOS: a launchd daemon
  (`/Library/LaunchDaemons/com.meabed.tailscale-proxy.plist`, log
  `/var/log/tailscale-proxy.log`). Linux: a systemd unit (`tailscale-proxy.service`,
  `journalctl -u tailscale-proxy`).
- **Updates without a password or a dropped request**: any newer tsp you run copies itself
  into `~/.tsp/bin` (never an older one), and the proxy checks for a release once a day and
  verifies it against the release's `checksums.txt`. The supervisor starts the new version
  beside the serving one on the same sockets; once it answers a real HTTPS request it takes
  over and the old worker drains. A version that fails, or crashes within its first minute,
  is recorded as set aside in `bin/state.json` and never used again; the previous worker
  keeps serving. A crashing worker restarts with backoff. sudo is needed again only if the
  supervisor itself changes, which `tsp doctor` says. `tsp run` in a terminal sets up a machine that has no proxy yet; in CI or
  a pipe it only warns.
- **Trust**: `tsp service install` ends with it (or `tsp trust` alone). macOS adds the CA
  to your login keychain (one password dialog at the screen; over SSH it is left as a
  next step). Debian/Ubuntu: `/usr/local/share/ca-certificates` +
  `update-ca-certificates`; Fedora/RHEL: `/etc/pki/ca-trust/source/anchors` +
  `update-ca-trust`. Windows: the user's Root store (`certutil -user`).
